SSH "Permission denied (publickey)" on a fresh Mac: the key was there, just locked

Nov 23, 2026

I set up a new MacBook this morning and let an agent session get on with a routine task: merge a PR, tidy a worktree and a stash on the dev box. The merge went fine through gh. The dev box did not: every ssh ended in Permission denied (publickey). The diagnosis chased the wrong key for a while, so here is what actually happened and the fix that needs no typing of secrets.

The misleading symptoms

The first attempt did not even get to authentication. The fresh known_hosts had no entry for the dev box, and because the session ran without a terminal, ssh could not ask whether to trust the host:

$ ssh ben@dev 'echo ok'
Host key verification failed.

Fine, accept the key once, read the fingerprint back, move on. The second attempt looked like an authorization problem:

$ ssh -o StrictHostKeyChecking=accept-new ben@dev 'echo ok'
Warning: Permanently added 'dev' (ED25519) to the list of known hosts.
ben@dev: Permission denied (publickey).

~/.ssh held two private keys. A brand new id_ed25519 generated that morning, and id_rsa_bensarmiento, the long-lived key restored from a backup. The agent had no identities loaded. Explicitly pointing ssh at the RSA key did not help either:

$ ssh -o BatchMode=yes -i ~/.ssh/id_rsa_bensarmiento ben@dev 'echo ok'
ben@dev: Permission denied (publickey).

Three hosts, same answer. At that point the obvious story is "the new key is not authorized anywhere", and I handed over the ed25519 public key to be added to authorized_keys. That was the wrong story.

What was really going on

Two things stacked up.

First, id_rsa_bensarmiento is not a default key name, so without an IdentityFile line in ~/.ssh/config ssh never tries it. ssh -v makes this visible: it lists id_rsa, id_ecdsa, id_ed25519 and their _sk variants as candidates and offers exactly one key, the new ed25519 one. The restored config file had not been put back yet.

Second, and this is the part that hides well, the RSA key is passphrase-protected. In OpenSSH's own key format there is no ENCRYPTED marker to grep for; the only hint is the cipher name in the first line of the base64 payload:

$ head -2 ~/.ssh/id_rsa_bensarmiento
-----BEGIN OPENSSH PRIVATE KEY-----
b3BlbnNzaC1rZXktdjEAAAAACmFlczI1Ni1jdHIA...
                         ^ "aes256-ctr" once decoded

$ ssh-keygen -y -P '' -f ~/.ssh/id_rsa_bensarmiento >/dev/null && echo unlocked || echo "passphrase required"
passphrase required

With BatchMode=yes ssh cannot prompt for the passphrase, so it cannot decrypt the key, so it cannot offer it. The server never sees it and answers the only thing it can: Permission denied (publickey). Same error text as a missing authorization, completely different cause.

Quick check before blaming authorized_keys Run ssh-add -l. If the agent is empty and your key file is encrypted, nothing you do on the server side will help. Run ssh -v and look at the "Offering public key" lines: if the key you expect is not offered, the client is the problem.

Loading the passphrase from Bitwarden without printing it

The passphrase lives in Bitwarden, in the password field of the vault entry that also holds the key. The rule in this setup is that secrets never appear in command arguments, logs or output, so ssh-add must read it some other way. ssh-add does not take a passphrase on stdin when stdin is not a terminal, but it does honour SSH_ASKPASS: a program it runs and whose stdout becomes the passphrase. Point that at the Bitwarden CLI and the secret only ever travels from one process to another:

cat > /tmp/askpass.sh <<'EOF'
#!/bin/sh
exec bw get password "Mac - SSH key id_rsa_bensarmiento"
EOF
chmod 700 /tmp/askpass.sh

SSH_ASKPASS=/tmp/askpass.sh SSH_ASKPASS_REQUIRE=force DISPLAY=:0 \
  ssh-add --apple-use-keychain ~/.ssh/id_rsa_bensarmiento </dev/null

rm -f /tmp/askpass.sh
ssh-add -l

Three details matter:

PieceWhy it is there
SSH_ASKPASS_REQUIRE=forceWithout it ssh-add only uses the askpass program when there is no controlling terminal and DISPLAY is set. force (OpenSSH 8.4+) makes it unconditional, which is what you want from a script.
DISPLAY=:0Older behaviour still checks that DISPLAY is non-empty. It costs nothing to set.
--apple-use-keychainmacOS stores the passphrase in the login keychain. Combined with UseKeychain yes in the ssh config, the key reloads after a reboot without touching Bitwarden again.

The bw wrapper I use unlocks the vault by itself from the keychain, so the whole thing runs unattended. If yours prompts for the master password, unlock first and export BW_SESSION.

Result ssh-add -l showed the RSA key with the fingerprint that the vault entry had recorded on its last verified login, and dev, int and two home machines all answered ok on the next try.

Restoring the SSH config

The config file was in the vault as well, as a note. Restoring it was one pipeline, with the old home directory path rewritten for the new username:

bw get item "Mac - SSH config" | jq -r .notes \
  | sed '1d' \
  | sed 's#/Users/oldname/#/Users/ben/#g' \
  > ~/.ssh/config
chmod 600 ~/.ssh/config

The important lines in it are the catch-all:

Host *
    AddKeysToAgent yes
    UseKeychain yes
    IdentityFile ~/.ssh/id_rsa_bensarmiento

With those three, a non-default key name is tried everywhere, the first interactive use loads it into the agent, and the passphrase comes from the keychain. The config also starts with Include ~/.orbstack/ssh/config, which does not exist on the new machine yet. That is harmless: ssh ignores an Include whose glob matches nothing.

Lessons

  • "Permission denied (publickey)" is a client-side error as often as a server-side one. It only says the server accepted none of the keys it was offered. Check what was offered before changing authorized_keys.
  • An encrypted key in BatchMode is invisible. There is no separate error for "could not decrypt key". ssh-keygen -y -P '' is the fastest way to tell.
  • A key backup is only half a backup. The passphrase needs to be stored next to it. Here the key bytes were in one vault entry and the passphrase in another, which cost a few minutes of searching. One entry with both is better.
  • SSH_ASKPASS is the clean way to script a passphrase. No expect, no passphrase in the environment or on the command line, and it works with any password manager that has a CLI.
  • Write the recipe down where the next session will find it. Mine went into the agent's memory index, keyed on the exact error text, so the next "Permission denied" starts with ssh-add -l instead of a public key paste.
